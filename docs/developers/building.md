# Building & releases

nameIT is a [Flutter](https://flutter.dev) app for Android (iOS-ready).

## Run it locally

Requires Flutter 3.38 or newer (`flutter --version`).

```bash
flutter create --platforms=android,ios --org at.nameit --project-name nameit .   # generates android/ and ios/, keeps lib/
dart run tool/setup.dart                                  # adds permissions, sets the app name
flutter pub get
dart run flutter_launcher_icons                           # app icon for Android + iOS
flutter run                                               # with a phone or emulator connected
```

`android/` and `ios/` are not committed – they are generated by
`flutter create`, and `tool/setup.dart` patches in what nameIT needs
(internet and camera permissions, app name, release signing).

APK for your own phone:

```bash
flutter build apk --release
# → build/app/outputs/flutter-apk/app-release.apk
```

## Tests

```bash
flutter test        # CSV import, WebUntis login parsing, TOTP, badges
flutter analyze
```

The [screenshot test](docs-and-screenshots.md) lives in `screenshot_test/`
and is not part of this run.

## Continuous integration

[`.github/workflows/build-apk.yml`](https://github.com/lukasdiem/nameit/blob/main/.github/workflows/build-apk.yml)
runs on every pull request and every push to `main`:

| Job | What it does |
|---|---|
| **check** | `flutter analyze` (report only) and `flutter test` |
| **build** | release APK for arm64, signed with the stored key, signature verified |
| **release** | publishes the APK on GitHub (not for pull requests) |

Changes to documentation only (`docs/`, `*.md`, `mkdocs.yml`, the demo data
and screenshot test) don't start an APK build.

## Versions

* **Version name** comes from `version:` in `pubspec.yaml`, e.g. `0.2.0`.
* **Build number** (Android `versionCode`) is the workflow run number, so it
  always goes up and new builds install over old ones.
* Every push to `main` publishes a **pre-release** `v0.2.0-build.42`.
* Pull request builds attach the APK as a workflow artifact (kept 14 days).

### Publishing a release

1. Bump `version:` in `pubspec.yaml` and merge.
2. Tag the commit:

    ```bash
    git tag v0.2.0 && git push origin v0.2.0
    ```

The build fails if the tag doesn't match `pubspec.yaml`. The release gets
notes generated from the merged pull requests and is marked **Latest**.

## Signing

All builds are signed with the same key, stored base64-encoded in the
repository secret `SIGNING_KEYSTORE`. Without the same key Android refuses
to install a new version over an old one – and uninstalling would delete the
teacher's data. Builds on `main` fail if the secret is missing; pull request
builds fall back to a throwaway key with a warning.
